# CapitalTracker — Engineering Guidelines for AI Agents

Машинно-читаемое техническое задание и архитектурный регламент для AI-ассистентов команды ИВТ-262 (Павловский И. Ю., Ларченко И. М.). Документ дополняет проектное техническое задание `README.md` и отчет по лабораторной работе № 3 `docs/laba_3.md`.

Файл составлен на основе требований к лабораторным работам по дисциплине «Программная инженерия» (ВолгГТУ, 2026 г.) и задает правила перехода от консольного прототипа ядра к целевому веб-приложению.

## 1. Назначение и границы системы (Project Scope)

**CapitalTracker** — автономная система ручного персонального финансового учета и контроля бюджетов.

* **Реализуемый функционал (Scope по README.md):**
  * Учет мультивалютных и разнотипных счетов: дебетовые карты (`DEBIT`), кредитные карты с поддержкой отрицательного баланса (`CREDIT`), наличные средства (`CASH`), накопительные счета (`SAVINGS`).
  * Регистрация доходов (`INCOME`) и расходов (`EXPENSE`) с обязательной привязкой к счетам и категориям.
  * Межбалансовые переводы (`TRANSFER`) между своими счетами без изменения совокупного капитала.
  * Бюджетирование: установка месячных лимитов по категориям и трехцветный индикатор освоения (`GREEN` < 80%, `YELLOW` 80–100%, `RED` > 100%).
  * Доработка проекта: выгрузка отфильтрованного журнала транзакций в плоский файл `CSV UTF-8 с BOM`.
  * Безопасное архивирование счетов вместо физического удаления для сохранения истории проводок.

* **Границы системы (Вне Scope проекта):**
  * НИКАКИХ банковских API, парсеров смс или интеграций со шлюзами (Сбер, Т-Банк и т.д.).
  * НИКАКИХ запросов номеров карт, CVC-кодов или банковских паролей.
  * НИКАКИХ общих семейных бюджетов (в рамках учебного этапа каждый профиль изолирован по `user_id`).

## 4. Архитектурные правила и код-стайл (Do / Don't)

### 4.1. Контракты репозиториев: только `abc.ABC`

По требованию код-ревью кафедры САПР и ПК утиная типизация (`typing.Protocol`) запрещена. Используются явные абстрактные базовые классы с наследованием.

```python
# DON'T — не использовать Protocol для репозиториев
from typing import Protocol

class AccountRepositoryProtocol(Protocol):
    def get_by_id(self, account_id: int) -> Account | None: ...

# DO — использовать abc.ABC и декоратор @abstractmethod
from abc import ABC, abstractmethod

class AccountRepository(ABC):
    """Абстрактный контракт взаимодействия с хранилищем счетов."""

    @abstractmethod
    def get_by_id(self, account_id: int) -> Account | None:
        """Возвращает счет по идентификатору."""
```

### 4.2. Перечисления: `StrEnum` в моделях, `IntEnum` в CLI

Для моделей используется `StrEnum` (Python 3.11+). Множественное наследование `class X(str, Enum)` запрещено линтером (правило `UP042`). В CLI выбор пунктов меню выполняется строго через `IntEnum` с валидацией диапазона, без молчаливых замен на дефолт.

```python
# DON'T — устаревший (str, Enum) и дефолтная подстановка при неверном вводе
class AccountType(str, Enum):
    DEBIT = "DEBIT"

choice = input("Тип: ")
acc_type = type_map.get(choice, AccountType.DEBIT)  # Подмена мусора на DEBIT!

# DO — StrEnum в моделях и безопасный IntEnum в CLI
from enum import IntEnum, StrEnum

class AccountType(StrEnum):
    DEBIT = "DEBIT"
    CREDIT = "CREDIT"
    CASH = "CASH"
    SAVINGS = "SAVINGS"

class AccountTypeChoice(IntEnum):
    DEBIT = 1
    CREDIT = 2
    CASH = 3
    SAVINGS = 4
```

### 4.3. Точность финансовых расчетов: `Decimal` и `is_finite()`

Для денежных величин категорически запрещен тип `float`. Перед выполнением операции сумма проверяется на конечность (`not amount.is_finite()`) для защиты от `Infinity` и `NaN`.

```python
# DON'T — использование float или пропуск проверки на конечность
def register_transaction(self, amount: float):
    if amount <= 0:
        raise ValueError()

# DO — строго Decimal, конечное положительное число
from decimal import Decimal

def register_transaction(self, amount: Decimal):
    if not amount.is_finite() or amount <= Decimal("0.00"):
        msg = "Сумма операции обязана быть конечной и строго положительной."
        raise ValueError(msg)
```

### 4.4. Разделение слоев: CLI никогда не лезет в репозитории

Терминальный интерфейс общается исключительно с сервисами (`AccountService`, `CategoryService` и т.д.). Прямой доступ к репозиториям из интерфейса запрещен.

```python
# DON'T — прямой доступ CLI к базе данных/репозиторию
class TerminalInterface:
    def __init__(self, category_repo: CategoryRepository) -> None:
        self._cat_repo = category_repo  # Нарушение архитектурных слоев!

# DO — вызов бизнес-логики через соответствующий сервис
class TerminalInterface:
    def __init__(self, category_service: CategoryService) -> None:
        self._cat_svc = category_service
```

### 4.5. Стандарты документирования и чистоты функций

1. **Docstrings:** каждый класс, метод и функция должны иметь понятное описание на русском языке под сигнатурой.
2. **Внутристрочные комментарии:** комментарии `# ...` внутри тел функций и методов **запрещены** (требование лабораторной работы № 3).
3. **Длина строки:** максимум **88 символов** (настройка Ruff). Длинные сообщения разбиваются в круглых скобках `(...)`.

## 5. Доменные правила и инварианты (Business Rules)

При реализации и модификации сервисов соблюдай требования технического задания:

1. **Изоляция данных по пользователю (`user_id`):**
   * Любая операция со счетом, категорией или транзакцией обязана проверять `entity.user_id == user_id`.
   * При попытке доступа к чужой сущности выбрасывается `PermissionError`.
   * Примечание: в консольном MVP Лабораторной № 3 `user_id = 1` зафиксирован как осознанное ограничение прототипа (задокументировано в `main.py`).

2. **Соответствие типа операции и направления категории:**
   * Нельзя связать расходную операцию (`TransactionType.EXPENSE`) с категорией дохода (`CategoryDirection.INCOME`).
   * Нельзя связать доходную операцию (`TransactionType.INCOME`) с категорией расхода (`CategoryDirection.EXPENSE`).

3. **Инвариант межбалансового перевода:**
   * Перевод возможен только между двумя разными счетами одного владельца (`from_account_id != to_account_id`).
   * Баланс списания уменьшается на сумму `amount`, баланс зачисления увеличивается на `amount`.
   * **Совокупный капитал пользователя до и после перевода остается неизменным.**

4. **Атомарность и корректность отката (`delete_transaction`):**
   * Удаление расхода возвращает деньги на счет (`balance + amount`).
   * Удаление дохода списывает деньги со счета (`balance - amount`).
   * При удалении перевода сначала проверяется существование обоих счетов, и только затем корректируются оба остатка. Деньги не должны теряться.

5. **Архивация счетов (REQ-ACC-02):**
   * Счета, по которым проходили операции, не удаляются физически, а помечаются `is_archived = True`.
   * Архивные счета скрываются из списка активных и исключаются из расчета капитала, но сохраняются в истории операций.

6. **Контроль бюджетов:**
   * Месяц проверяется в диапазоне строго от 1 до 12.
   * При расчете суммы учитываются только транзакции с типом `EXPENSE` за выбранный месяц и год.
   * Границы светофора: строго до 80% — `GREEN`, от 80% до 100% включительно — `YELLOW`, свыше 100% — `RED`.

7. **Экспорт журнала в CSV (Результат доработки):**
   * Поток формируется через `io.StringIO` с разделителем `;` и обязательной сигнатурой `UTF-8 BOM` (`\ufeff`) для корректного открытия русских символов в Excel.

## 6. Команды для запуска и проверки проекта

Все команды выполняются через пакетный менеджер `uv` из корня проекта:

```bash
# Синхронизация зависимостей окружения
uv sync

# Сборка пакета (проверка корректности структуры проекта)
uv build

# Запуск консольного приложения (вариант 1 - по имени скрипта)
uv run capital-tracker

# Запуск консольного приложения (вариант 2 - запуск модуля)
uv run python -m src.main

# Проверка кода линтером Ruff (длина строк, неиспользуемые импорты, PEP 8)
uv run ruff check src/

# Проверка форматирования
uv run ruff format --check src/
```

## 7. Чек-лист частых ошибок (Anti-patterns)

| Что сделано не так | Почему это ошибка в проекте | Как исправить |
|---|---|---|
| Использован `float` для баланса | Накапливаются ошибки двоичного округления копеек | Использовать только `Decimal` |
| Пропущен `amount.is_finite()` | Пропускает `Infinity` и `NaN`, ломая математику | Добавить проверку `if not amount.is_finite():` |
| Объявлен `class X(str, Enum):` | Ошибка линтера `UP042` для версии Python 3.11+ | Наследовать напрямую от `StrEnum` |
| Оставлены комментарии `# ...` внутри функций | Нарушение требований к стилю кода лабы | Оставлять только docstrings под объявлением функции |
| Строка в коде длиннее 88 символов | Ошибка линтера `E501 Line too long` | Перенести части выражений в круглых скобках |
| Прямой вызов репозитория из интерфейса | Нарушение принципов чистой слоистой архитектуры | Проводить вызов через `CategoryService` |
| Расход записан на категорию «Зарплата» | Нарушение доменной логики учета финансов | Добавить проверку `category.direction` в сервисе |
| Запуск `python src/main.py` из папки `src/` | Ошибка `ModuleNotFoundError: No module named 'src'` | Запускать из корня через `uv run capital-tracker` |
| Добавлены сторонние сервисы (JWT, Celery, Redis) | Избыточный оверхед, не заявленный в README проекта | Следовать утвержденному стеку проекта |

## 8. Краткая шпаргалка (Quick Reference)

* **Деньги и суммы:** `Decimal` + `not amount.is_finite() or amount <= Decimal("0.00")`.
* **Абстракции доступа к данным:** `class RepositoryName(ABC):` с `@abstractmethod`.
* **Перечисления моделей:** `class ModelEnum(StrEnum):`.
* **Меню и выбор в терминале:** `class ChoiceEnum(IntEnum):` + обработка ввода в цикле.
* **Связка компонентов:** внедрение зависимостей через конструкторы (`Dependency Injection`) в `main.py`.
* **Проверка перед сдачей:** `uv run ruff check src/` -> `All checks passed!`.
