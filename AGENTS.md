# CapitalTracker — Engineering Guidelines for AI Agents

Технические правила работы с учебным проектом команды ИВТ-262
(Павловский И. Ю., Ларченко И. М.). Учитывать требования преподавателя,
ТЗ в `README.md` и фактическое состояние исходников.

## 1. Границы работы и документация

* `README.md` — ТЗ целевого веб-приложения; не редактировать без отдельного
  согласования. `docs/laba_3.md` — исторический отчет об InMemory-прототипе:
  сохранять исходные листинги и описание этапа, допускаются точечные
  пояснения о последующих изменениях в лабораторной № 4.
* Текущая реализация лабораторной № 4 — консольный интерфейс с PostgreSQL,
  SQLAlchemy, мапперами доменных датаклассов и миграциями Alembic.
  Отчет находится в `docs/laba_4.md`, ER-схема — в `docs/er.md`.
* При изменении реализации актуализировать соответствующие листинги отчета
  из настоящих файлов, включая форматирование Ruff. Не придумывать результаты
  команд и тестов. Сначала выполнить проверку, затем записать результат.
* Не добавлять возможности за пределами задачи, не менять архитектуру
  ради примера из методички. Временные планы из переписки не копировать
  в технические инструкции.
* Этот файл — инструкции для ассистента, а не запускаемый агент приложения.
  Актуализировать его по итоговой реализации, а не после каждой мелкой правки.

## 2. Назначение и утвержденный стек

CapitalTracker — ручной персональный финансовый учет: счета, доходы,
расходы, переводы, месячные бюджеты, история и CSV. Типы счетов:
`DEBIT`, `CREDIT`, `CASH`, `SAVINGS`; отрицательные остатки разрешены.

Не подключать банковские API, распознавание SMS, платежные шлюзы,
семейные бюджеты. Не запрашивать номера карт, CVC или банковские пароли.
Данные разных пользователей изолируются по `user_id`.

Ограничения зависимостей задает `pyproject.toml`, разрешенные версии —
`uv.lock`. Не добавлять несогласованные пакеты или инфраструктуру.

| Компонент | Ограничение / применение |
| :--- | :--- |
| Python | `>=3.11`; `StrEnum`, `IntEnum`, объединения `X \| Y` |
| uv | Установка, запуск, сборка и проверка проекта из корня |
| SQLAlchemy | `>=2.0.0`; синхронные ORM и Session, `Mapped` / `mapped_column` |
| Alembic | `>=1.13.0`; единственный способ создания и изменения схемы |
| Psycopg | `psycopg[binary]>=3.2.0`; URL с `postgresql+psycopg` |
| PostgreSQL | `postgres:15` в `docker-compose.yaml`, согласно ТЗ |
| FastAPI, Pydantic | `>=0.110.0`, `>=2.6.0`; зависимости будущего веб-этапа |
| Ruff | `>=0.3.0`; 88 символов, Python 3.11, `E,F,I,N,UP,B,A,C4,SIM` |

| pytest | `>=8.0.0`; интеграционные сценарии на PostgreSQL |
| uv_build | `>=0.13.1,<0.14.0`; `module-name = "src"`, `module-root = "."` |

Не вводить JWT, Redis, Celery, асинхронный стек, дополнительные библиотеки
настроек или новые сущности, если это не требуется поставленной задачей.
Веб-авторизация предусмотрена ТЗ, но не реализуется в консольной лабораторной.

  InMemory остаются в исходниках, но не используются в штатной DI-сборке.
* Фасады `repositories/__init__.py` и `services/__init__.py` используют
  явные экспорты `__all__`. Не возвращать устаревшие пути `*_service.py`
  или разделение репозиториев на `base.py` / `in_memory.py`.
* Бизнес-валидация находится в сервисах. CLI только преобразует ввод,
  выбирает `IntEnum`, вызывает сервисы и форматирует вывод. Прямые обращения
  из CLI к репозиториям, Session или ORM запрещены.

## 4. DB-First, схема и миграции

### 4.1. Порядок проектирования

Сначала определить ER-схему, ключи, обязательность полей, ограничения
и каскады. Затем описать согласованную схему ORM-моделями, сгенерировать
и проверить миграцию, применить ее и адаптировать прикладной код.
Миграции хранят историю схемы, ORM-модели — ее текущее состояние.

Все ORM-модели наследуются от одного `Base` из `src/database/base.py`.
Колонки описываются через `Mapped` / `mapped_column`. У каждой таблицы
есть PK, у связей — FK. Общая metadata использует соглашение именования
PK, FK, UNIQUE, CHECK и индексов. CHECK-ограничения именуются явно.

**Не использовать `Base.metadata.create_all()` нигде: ни в приложении,
ни в тестах, ни в инициализации. Схему создает только Alembic.**

### 4.2. Текущие ограничения

* Основные таблицы: `users`, `accounts`, `categories`, `transactions`,
  `budget_limits`. Все PK `id` генерируются БД. У нового доменного объекта
  `id=0`, маппер не переносит нулевой ID в новую ORM-запись.
* Email пользователя уникален. Имена пользователей, счетов и категорий
  не могут быть пустыми. Перечисления хранятся строками с CHECK,
  без отдельного PostgreSQL Enum-типа.
* Счета и категории имеют `UNIQUE(user_id, id)` для составных FK.
  Операции ссылаются на счет, целевой счет и категорию вместе с `user_id`.
  Лимиты аналогично ссылаются на категорию своего владельца.
  Обычный FK по ID не заменяет проверку совпадения владельца.
* У дохода/расхода обязательна категория и отсутствует целевой счет.
  У перевода нет категории, целевой счет обязателен и отличается от исходного.
  Структуру операции дополнительно защищает CHECK БД.
* Лимит уникален по `(user_id, category_id, month, year)`; месяц 1–12,
  год 1970–2100. SQLAlchemy-репозиторий при повторной установке меняет сумму,
  сохраняя ID существующего лимита.
* Все финансовые поля — `NUMERIC(18, 2)`; ограничения диапазона не пропускают
  `NaN` и бесконечность. Денежная валидация до SQL обязательна.
* Время хранится без часового пояса, как в прототипе; календарные периоды
  бюджета используют локальное время приложения. Не менять эту политику
  без согласованного изменения расчетов и схемы.
* История и списки возвращаются в порядке добавления (`ORDER BY id`).
  У финансовых дочерних таблиц индексируется `user_id`, у операций также
  `account_id`, `category_id`, `to_account_id`, у лимитов — `category_id`.

### 4.3. Связи и каскады

Владельцы и дочерние сущности связаны через `relationship` / `back_populates`.
У счета две разные связи с операциями: основной счет и целевой счет перевода.
Их `primaryjoin` и `foreign_keys` указываются явно, иначе связь неоднозначна.

Связь M:N счетов и категорий хранится через существующие `transactions`:
`AccountORM.categories` ↔ `CategoryORM.accounts`. Используются `secondary`,
`back_populates`, `viewonly=True`. Это отражение фактической истории;
переводы без категории не добавляют связь. Повторные операции одной пары
допускаются и имеют разные ID. Не создавать вторую таблицу связи или метки
только ради демонстрации M:N.

Нельзя создавать финансовую операцию простым `append` в M:N-коллекцию:
нужны сумма, тип, дата и корректировка баланса через сервис. Уже загруженные
viewonly-коллекции после изменения операций перечитываются через
`Session.expire` или новую сессию.

Все FK используют `ON DELETE RESTRICT`. Связи 1:N не имеют каскадного
удаления: остаются `save-update, merge`, а `passive_deletes="all"`
не дает ORM обнулить FK даже при загруженных коллекциях. Счет архивируется,
операции сохраняются. Не копировать `all, delete-orphan` из библиотечного
примера: удаление финансовой истории противоречит предметной области.

### 4.4. Практика Alembic

* `alembic.ini` и `migrations/` находятся в корне. Не называть каталог
  `alembic/`: он может перекрыть импорт установленного пакета.
* `env.py` загружает все модели и передает общую metadata. Импорт `Base`
  из модуля моделей явно реэкспортирован (`Base as Base`), что учитывает
  строгий mypy. Пустая metadata означает ошибку регистрации моделей.
* Приложение и Alembic читают один `DATABASE_URL` из настроек.
  Тесты передают свое подключение через `config.attributes["connection"]`.
* `revision --autogenerate` формирует кандидат. Перед применением проверить
  все таблицы, FK, CHECK, UNIQUE, индексы и обратный порядок `downgrade`.
  Пустую ревизию вместо ожидаемых изменений не применять.
* При автогенерации строковых Enum возможны повторные CHECK. В ревизии
  оставить один явно именованный CHECK и выключить создание второго у типа
  Enum (`create_constraint=False`). В модели проверка остается включенной.
* После автогенерации убрать комментарии внутри функций, добавить русские
  docstrings и отформатировать код. Длинные SQL-строки разбивать на соседние
  строковые литералы в скобках, не отключать правило E501.
* Примененную миграцию не переписывать для изменения схемы. Создавать новую
  ревизию; не удалять историю. Проверять `alembic check` и обратимость
  на отдельной тестовой БД, а не на прикладных данных.
* Автогенерация не заменяет ручную проверку переименований, переноса данных
  и изменения ограничений. Не выдавать успешный `alembic check`
  за проверку всех бизнес-правил.

## 5. Сессии, DI и атомарность

* Движок создается один раз, Session — на одну команду CLI.
  Глобальную сессию на весь сеанс приложения не создавать.
* `build_interface(session, user_id)` передает одну общую сессию всем
  SQLAlchemy-репозиториям. Репозитории не создают Session, не делают
  `commit()` и не содержат бизнес-правил; `flush()` получает ID и проверяет SQL.
* `run_application()` открывает `SessionFactory.begin()` вокруг `run_once()`.
  Успех фиксируется после команды, исключение откатывает весь набор изменений.
  Ошибки команд изменения данных не поглощаются внутри обработчиков CLI
  до завершения контекста: иначе можно ошибочно зафиксировать частичное
  изменение остатков. Ошибки фильтрации при чтении обрабатываются в CLI
  с отменой действия; эти обработчики не изменяют данные.
* `IntegrityError` и `DataError` обрабатываются после отката. PostgreSQL
  для бесконечности в `NUMERIC(18, 2)` возвращает `DataError`, а для нарушений
  CHECK / FK / UNIQUE / NOT NULL — `IntegrityError`.
* Перевод, запись журнала и удаление с компенсацией используют одну внешнюю
  транзакцию. При прямом вызове сервисов вызывающий код обязан предоставить
  такую границу. Последовательные вызовы сервисов сами не заменяют транзакцию.
* При старте `initialize_profile()` повторяемо создает профиль CLI по email
  `cli@capitaltracker.local` и категории. Не полагаться на `user_id=1`:
  ID выдает БД, значение сохраняется и передается в сервисы.
* Маркер `!disabled` в учебной записи не является хэшем пароля и не используется
  для аутентификации. Не представлять bootstrap-профиль как реализацию входа.

## 6. Бизнес-правила и финансовая точность

### 6.1. Деньги

Категорически не использовать `float`. Все суммы — `Decimal`.
Общая функция `src/services/money.py:validate_money` проверяет:

1. Конечность через `is_finite()` до любых сравнений и округлений.
2. Строгую положительность суммы операции / перевода / лимита.
3. Диапазон `NUMERIC(18, 2)` до `9999999999999999.99` по модулю.
4. Точность до копеек без изменения суммы. `1.2300` допустимо,
   `0.005` отклоняется. Не округлять два остатка перевода независимо.

Начальный баланс может быть нулевым или отрицательным, но обязан быть
конечным и укладываться в денежный формат. Непустое имя счета проверяется
в `AccountService`, а не только в интерфейсе.

### 6.2. Владельцы и категории

* Сервисы проверяют `entity.user_id == user_id`. Попытка использовать
  чужую сущность вызывает `PermissionError`. SQL-составные FK дополняют,
  но не заменяют сервисную проверку.
* `TransactionService` и `BudgetService` получают обязательный репозиторий
  категорий. Не возвращать `category_repo=None` и обход проверки категории.
* Доходы и расходы требуют существующей категории соответствующего
  направления. Для перевода использовать только `make_transfer`.
* `CategoryService.get_by_id` принимает и ID категории, и ID владельца.
  Чужая категория недоступна; отсутствующая возвращает `None`.

### 6.3. Переводы, удаление и архив

* Счета перевода различаются, принадлежат одному пользователю и активны.
  Списание уменьшает один остаток, зачисление увеличивает другой на ту же сумму;
  совокупный капитал не меняется.
* Новые операции и переводы по архивным счетам запрещены сервисом.
  Архивные счета исключены из активного капитала, но доступны через репозиторий
  по ID для истории и отмены прежних операций.
* Удаление расхода возвращает сумму; удаление дохода списывает ее.
  Перед отменой перевода проверяются наличие и владелец обоих счетов,
  затем оба остатка и журнал меняются в общей транзакции.
* Архивация не удаляет записи. `archive_account` проверяет владельца
  и при чужом счете вызывает `PermissionError`.

### 6.4. Бюджеты и CSV

* Период проверяется в сервисе и при установке, и при расчете статуса.
  Лимит — положительный конечный `Decimal`, категория — расходная.
* Учитываются только `EXPENSE` выбранной категории, владельца, месяца и года.
  До 80% — GREEN; от 80% до 100% включительно — YELLOW; свыше 100% — RED.
  `calculate_status` возвращает расходы, процент и строку с цветом и пояснением.
* `seed_defaults` добавляет «Продукты», «Кафе» и «Зарплата», только если
  у пользователя нет категорий. CLI получает категории через сервис.
* Экспорт использует `io.StringIO`, `csv.writer`, разделитель `;` и BOM
  `\ufeff` в начале строки. Сервис возвращает `str`, CLI записывает
  `transactions_export.csv` с `encoding="utf-8"`. Второй BOM добавлять нельзя.
* Столбцы: ID, дата/время, тип, счет, категория, сумма в рублях.
  Дата `%Y-%m-%d %H:%M:%S`, сумма с двумя знаками после точки;
  запасные значения — «Неизвестный» и «Без категории».
* Контракт экспорта: `export_to_csv(user_id, transactions)`. До формирования
  CSV ExportService проверяет владельца каждой операции, исходного счета,
  категории (если она указана) и целевого счета перевода (если он указан).
  При отсутствии связанной сущности или несовпадении владельца вызывается
  `PermissionError`. Проверки выполняются для всего списка до создания CSV.

### 6.5. История операций и фильтры

* `TransactionService.get_history` поддерживает фильтры `date_from`,
  `date_to`, `account_id`, `category_id`, `tx_type`. Границы дат включительные;
  все заданные фильтры объединяются через AND.
* Начальная дата не может быть позже конечной. Счет и категория проверяются
  на существование и принадлежность пользователю; иначе вызывается
  `PermissionError`. Для фильтра счета учитываются исходный и целевой счета.
* CLI использует общий `_read_history_filters` для просмотра истории
  и экспорта. Пустое поле означает отсутствие соответствующего фильтра;
  некорректный ввод или ошибка сервиса прерывает операцию, а не запускает
  вывод или экспорт нефильтрованной истории.
* `_handle_show_history` возвращает `bool`: при ошибке фильтра или пустой
  выборке — `False`. Удаление в этом случае отменяется без запроса ID.
* Ошибки открытия и записи CSV (`OSError`) обрабатываются в CLI:
  пользователь получает сообщение об ошибке и возвращается в меню.
  Сообщение об успешном экспорте выводится только после закрытия файла.

## 7. Стиль и интерфейс

* Каждый класс, метод и функция имеют понятный русский docstring
  непосредственно под сигнатурой. Требование относится и к `__init__`,
  свойствам, тестам и функциям миграций.
* Комментарии `# ...` внутри функций и методов запрещены. Не заменять
  docstrings строковыми комментариями в середине тела функции.
* Максимум 88 символов в строке. Ruff форматирует и проверяет код,
  mypy выполняет строгую проверку типов. Не подавлять ошибки без причины.
* Доменные перечисления наследуются от `StrEnum`, а не `(str, Enum)`.
* Главное меню и подменю используют `IntEnum`: `MainMenuChoice`,
  `AccountTypeChoice`, `TransactionKindChoice`, `HistoryTypeChoice`,
  `BudgetActionChoice`.
  Общий `_read_choice` повторяет запрос при ошибке, не выбирает значение
  по умолчанию. Не заменять пункты меню строковыми сравнениями.
* `run_once()` выполняет одну команду и возвращает признак продолжения.
  Цикл и граница транзакции находятся в точке сборки приложения.

## 8. Команды запуска и проверки

Из корня проекта:

```bash
uv sync
docker compose up -d --wait
uv run alembic upgrade head
uv run capital-tracker
```

Альтернатива запуска: `uv run python -m src.main`. Не запускать
`python src/main.py` из каталога `src/`.

Для миграций и проверки схемы:

```bash
uv run alembic revision --autogenerate -m "describe schema change"
uv run alembic current
uv run alembic history
uv run alembic check
```

Для проверок и сборки:

```bash
uv run ruff check src/ migrations/ tests/
uv run ruff format --check src/ migrations/ tests/
uv run mypy src/ migrations/ tests/
uv run pytest -q
uv build
```

### 8.1. Тестовая PostgreSQL

Один раз создать отдельную базу:

```bash
docker compose exec -T db createdb -U capitaltracker capitaltracker_test
```

`tests/conftest.py` использует ее по умолчанию либо читает
`TEST_DATABASE_URL`; имя БД обязано заканчиваться на `_test`.
Миграции применяются Alembic, данные тестов изолируются транзакциями.
Тест обратимости удаляет и восстанавливает схему этой тестовой БД.
Не направлять тесты на прикладную `capitaltracker`.

Проверки должны подтверждать остатки и откат при ошибке записи,
владельцев, ограничения PostgreSQL, обе стороны M:N, правила RESTRICT
для загруженных и незагруженных коллекций, бюджеты, CSV и сохранность
данных при новой сессии. Ruff и mypy не заменяют эти сценарии.

### 8.2. Docker и окружение

* Настройка `DATABASE_URL` читается через `os.getenv`. Файл `.env`
  не подхватывается Python автоматически. Compose-переменные и окружение
  локального процесса — разные вещи.
* С локального компьютера хост БД — `localhost`, внутри сети Compose — `db`.
  Менять URL вместе с изменением способа запуска.
* `docker compose down` сохраняет том. Не использовать `down -v`
  или удаление тома для обычного перезапуска: это удаляет данные.
* При `command not found: docker` на macOS проверить пользовательский путь
  `$HOME/.docker/bin`. Для текущего терминала:
  `export PATH="$HOME/.docker/bin:$PATH"`.
  Если CLI найден, но нет соединения с сокетом, запустить Docker Desktop
  и дождаться Engine running.

## 9. Git и оставшиеся границы реализации

В Git сохраняются исходники, миграции, Compose-конфигурация, тесты,
документация, `pyproject.toml`, `uv.lock`. Не игнорировать новые исходники
только потому, что они созданы инструментом.

`.gitignore` исключает `.venv/`, `.env` и локальные варианты `.env.*`
(кроме `.env.example`), кэши Python / Ruff / mypy / pytest, файлы macOS
и IDE, результаты сборки, покрытие тестов и CSV-выгрузку. Данные PostgreSQL
находятся в Docker-томе вне репозитория. Проверять `git status` и
`git check-ignore`; уже отслеживаемый файл не исчезает из индекса
после добавления правила.

Не считать реализованными авторизацию, API, веб-интерфейс и конвертацию валют.
В текущем CLI один учебный профиль и рублевый учет. История и экспорт CSV
поддерживают фильтры по датам, счету, категории и типу операции. Политика
конкурентных изменений из нескольких клиентов остается задачей веб-этапа.
Не вводить новые возможности только ради устранения этих осознанных ограничений.
